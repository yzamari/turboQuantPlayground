## State of the world right now

### Live VLM works end-to-end on Tab S9+

Verified on device today: tap **Live** → camera previews → first SmolVLM-256M caption appears after ~165 s on CPU. Captions are accurate (e.g. *"A bright light is on the ceiling."*). FPS chip reads `0.01 FPS · last 163956ms · 1 frames analyzed`.

The Live tab is **functional but slow on Tab S9+** because of an upstream bug, not our code:

- `mtmd_helper_eval_chunks` deadlocks on Adreno 740 / SD 8 Gen 2 at our pinned llama.cpp commit (`b8935` / `f454bd7e`).
- Reproduced by running upstream's stock `llama-mtmd-cli` with `-ngl 99` on the same device — same hang at "encoding image slice…" for both SmolVLM-256M and Qwen2.5-VL-3B.
- S24 Ultra (`pineapple`) runs the same code on Adreno fine.
- `VlmRunner.isAdrenoVlmKnownGood()` is the routing decision today: `pineapple`/`sun`/`8elite` → Adreno (`gpuLayers=99`); everything else → CPU (`gpuLayers=0`).

### Chat (LLM-only, no image) is unaffected

Both Tab S9+ and S24 Ultra run Llama-3.2-1B chat on Adreno (~30+ tok/s). The bug is specific to the mtmd vision pipeline.

## The user's open ask: "lets also do qnn and htp"

This needs scoping with the user before any code lands. There are three meaningfully different things "do QNN/HTP" could mean, and they have very different costs and payoffs.

### Option A — Wire the *existing* QNN scaffold into the Android build (small, ~1–2 days)

The repo already has a complete QNN backend at `cpp/backends/qnn_htp/` that accelerates **two** TurboQuant kernels — `rotate()` and `value_dequant()` (8-bit only). Everything else delegates to `cpu_neon`. Build is gated on `QNN_SDK_ROOT`.

**What this would deliver:** Faster TurboQuant Path-1 kernels and (eventually) faster Path-2 chat with `kvType=3` once the custom ggml op lands (P2.1c Steps 2–5).

**What this would NOT deliver:** Anything for Live VLM. The QNN scaffold doesn't touch SigLIP / mmproj / mtmd at all.

Concrete steps:
1. Resolve QNN SDK distribution (Qualcomm dev account + accept license).
2. Add `QNN_SDK_ROOT` env wiring to `android/app/src/main/cpp/CMakeLists.txt`.
3. Push the four runtime `.so`s (`libQnnHtp.so`, `libQnnHtpV73Stub.so`, `libQnnSystem.so`, `libQnnHtpV73Skel.so`) into `jniLibs/arm64-v8a/` (V73 for SD 8 Gen 2 Hexagon; V75 for SD 8 Gen 3).
4. Verify the existing parity tests `cpp/tests/parity_test.cpp` pass with `--backend qnn_htp`.

### Option B — Port SigLIP to QNN to unblock Tab S9+ Live (large, multi-week)

This is what the user *probably* meant given the conversation context, but it's a much bigger project than Option A. SigLIP-base is a Vision Transformer (~96M params). Porting:

1. Export SigLIP-base / mmproj weights to QNN's `.bin` format via the QAIRT toolchain (Linux host required; macOS can't run the converter).
2. Build a QNN graph for the ViT — patch embed, 12 transformer blocks, projection head. Probably ~2 weeks of graph wiring + accuracy tuning.
3. Replace the call into `mtmd_helper_eval_chunks` with our SigLIP-on-HTP runner; the LLM continues on Adreno OpenCL via llama.cpp's existing path.
4. Validate cosine similarity vs FP32 reference at < 1e-3.

**Payoff if it works:** Tab S9+ Live VLM goes from 165 s/frame → ~50–100 ms/frame (HTP runs ViTs at ~10× Adreno speed and is also more power-efficient).

**Risks:**
- Hexagon HTP V73 (Tab S9+) is older than V75 (S24 Ultra); some ops may be unsupported.
- macOS dev can't run the conversion toolchain — needs a Linux machine or Docker.

### Option C — Use Qualcomm AI Hub's pre-exported VLM (medium, ~1 week)

Qualcomm's [AI Hub](https://aihub.qualcomm.com/) ships pre-quantized VLMs for HTP (e.g. [LLaVA-1.5](https://aihub.qualcomm.com/models/llava_v1_5_7b)). Replaces our llama.cpp/mtmd architecture with a parallel HTP-native pipeline for Live, while chat keeps using llama.cpp.

**Payoff:** Like Option B but no encoder porting — Qualcomm did it.

**Trade-off:** Architectural fork — Live tab and Chat tab use different runtimes. More moving parts to maintain.

### Recommended next step

**Brainstorm with the user (`/brainstorm`) before any code lands.** Specifically: what does "do QNN/HTP" mean to them — Option A, B, or C? Their answer changes the whole work plan. Cheapest interim experiment that *might* unblock Tab S9+ Live without the QNN cost is **Vulkan** (one evening — `GGML_VULKAN=ON` and see if mtmd doesn't deadlock there, since Adreno's Vulkan driver hits a different code path than its OpenCL driver).

## Reproducing the Tab S9+ Adreno+mtmd hang (for upstream bug report if needed)

```sh
adb push /tmp/llama.cpp/build/bin/llama-mtmd-cli /data/local/tmp/
adb push /sdcard/Android/data/com.yzamari.turboquant/files/SmolVLM-256M-Instruct-Q8_0.gguf /data/local/tmp/
adb push /sdcard/Android/data/com.yzamari.turboquant/files/mmproj-SmolVLM-256M-Instruct-Q8_0.gguf /data/local/tmp/
adb shell "cd /data/local/tmp && ./llama-mtmd-cli \
  -m SmolVLM-256M-Instruct-Q8_0.gguf \
  --mmproj mmproj-SmolVLM-256M-Instruct-Q8_0.gguf \
  --image any.jpg \
  -p 'describe' \
  -ngl 99"
```

Hangs at "encoding image slice…". Same binary with `-ngl 0` completes in ~165 s. Both SmolVLM-256M and Qwen2.5-VL-3B reproduce the same hang on `kalama`; neither hangs on `pineapple`.
